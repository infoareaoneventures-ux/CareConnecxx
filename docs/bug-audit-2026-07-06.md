## 0. Field-reported (from live SMS screenshots, 2026-07-06)

These came from real caregiver-onboarding transcripts and were traced to code.

### 0.1 [VERIFIED] [P0] Caregiver photo-upload link is never sent — signup dead-ends
**Where:** agent-native onboarding handoff —
`functions/src/linq/webhooks.ts:1862` → `handleCaregiverSendPhoto`
(`functions/src/agents/onboardingConversation.ts:2294`).

**Symptom (screenshot):** After the caregiver gives their "approach to care"
answer, Evia replies *"You're all set on this part, next I'll send the secure
step for your profile photo, then the rest of setup will follow by text."* — and
then **no link ever arrives**. The caregiver is stuck before photo → documents →
membership → background check, so the signup never completes.

**Root cause:** `bio` (the free-text "approach to care" prose) is a
**required** caregiver field (`onboardingContract.ts:79`). The profile-photo
link is only sent by the deterministic post-collection handoff at
`webhooks.ts:1862`, which fires **only** when the cursor has advanced to
`caregiver_send_photo` — and that advance (`webhooks.ts:1847`) requires
`missingRequiredFields(caregiver, curData) === 0`. In the agent-native path the
model *chats* an acknowledgment and a handoff promise but frequently does **not**
call `save_onboarding_field` for a long free-text bio, and the persistence-net
absorber (`absorbCaregiverFields`) can't reliably map prose into the `bio`
field. Result: `bio` stays missing → cursor never advances → handoff never fires
→ `handleCaregiverSendPhoto` never runs → the promised link is never sent. Evia
goes silent right after promising it.

**Fix options:**
- Make the closing/handoff line and the photo-link send **atomic**: when the
  model indicates collection is done, the deterministic handoff should run
  regardless, or the photo step should be triggered by the same tool call that
  the model uses to close collection (don't let the model free-text a promise
  that isn't wired to an action).
- Have `absorbCaregiverFields` treat any non-trivial free-text answer at the
  `caregiver_ask_bio` step as the `bio` value (prose doesn't need structured
  extraction — capture it verbatim), so the required-field net closes.
- Add a stuck-signup safety net: if a caregiver session sits at a collection
  step with only `bio` missing after the model already acknowledged it, force
  the advance to `caregiver_send_photo`.

### 0.2 [VERIFIED] [P0] "San Francisco works" immediately followed by "not in your area"
**Where:** `functions/src/linq/webhooks.ts:1828` (the persistence-net
service-area gate in the onboarding agent loop).

**Symptom (screenshot):** Caregiver texts "San Francisco 94102". Evia replies
*"Thanks, San Francisco works. How many years of caregiving experience do you
have?"* and then, in the same beat, *"I'm so sorry, we're not in your area just
yet. I've added you to our waitlist…"* — two directly contradictory messages.

**Root cause:** The agent's model turn composes and sends its acknowledgment
("SF works, next question") **before** the service-area gate runs. The gate is a
*post-turn* net: after the reply is already sent, `webhooks.ts:1809+` runs the
field absorber, sees the out-of-area city/zip, calls `parkOutOfArea`, and sends
the decline at line 1828. Because the model was never told SF is out of area at
the moment it acknowledged the location, it accepts + advances, and the gate
then reverses it.

**Fix:** The service-area verdict must be resolved **before** any
location-acknowledging reply is sent. Either:
- Handle the location collection step deterministically (scripted) with the gate
  inline, not via the free-form model turn; or
- Give the onboarding model a `check_service_area` tool it MUST call and await
  before acknowledging a location, and instruct it never to acknowledge/advance
  on location until the verdict is `in`. The prompt should make out-of-area a
  hard stop, not a thing the post-turn net cleans up.

Also note the decline copy here (`"I'm so sorry — we're not in your area just
yet…"`, line 1828) is a **third** wording distinct from
`gateOnboardingLocation`'s copy (`serviceAreaGate.ts:67`) and the `WAITLISTED_STEP`
re-prompt — three different out-of-area messages that should be unified.

### 0.3 [design, not a bug] "reply START OVER" reads robotic and over-resets
**Where:** `WAITLISTED_STEP` re-prompt (`onboardingConversation.ts:469`).

**Observation:** *"…If you're actually in Santa Clara County and I got that
wrong, reply START OVER and we'll try again. 💙"* Two issues:
1. The all-caps `START OVER` keyword feels like an IVR/SMS-bot command, off-voice
   for Evia (who is otherwise conversational). Prefer natural language: *"If I
   got that wrong and you're actually in Santa Clara County, just tell me the
   city or ZIP and I'll take another look."*
2. `START OVER` resets the **entire** session — re-asking role, name, everything
   — when only the *location* was wrong. The caregiver in the screenshot had to
   re-answer "are you looking for care or a caregiver" and re-enter their name.
   A location-only correction path (re-run just the service-area check against a
   new city/ZIP) would be far less punishing.

## 1. Backend — money, scheduling & onboarding state (P0/P1)

### 1.1 [VERIFIED] [P0] Refund flow is broken for every registered client
`functions/src/agents/refundHandler.ts:61` (+ callers
`linq/routeClient.ts:349`, `linq/routeIntent.ts:1589`). Sessions are keyed by
**phone** (`webhooks.ts:140`), but the refund handler writes its `refundStep`
state to `doc(session.userId ?? phone)`, and `userId` is the Firebase Auth uid
(`webhooks.ts:894`), not the phone. The router reads `refundStep` from the
phone-keyed doc, so for any registered client the state lands on the wrong
document, the flow resets every turn, and a refund can never be submitted via
SMS. **Fix:** pass/write `doc(phone)` consistently (mirror every other flow).

### 1.2 [VERIFIED] [P0] Double-reply on ~7 live intents
`functions/src/linq/routeIntent.ts:1441` (and the RESCHEDULE_REQUEST,
VIEW_INVOICE, VIEW_CARE_PLAN_HISTORY, VIEW_MY_JOBS/APPLICANTS/JOURNAL,
BROWSE_JOB_BOARD, CREDENTIAL_MANAGEMENT branches). These call `runQaAgent(...)` —
which already delivers its reply internally via `sendSplit(chatId)`
(`qaAgent.ts:2683`, gated only by `skipSend`, default off) — and **then** also
call `sendViaInteractionAgent` with the same text. The user gets two identical
bubbles. The default QA path (`routeIntent.ts:1830`) proves the contract: it
never calls `sendViaInteractionAgent`. **Fix:** drop the second send (or pass
`skipSend:true` to `runQaAgent` on these branches).

### 1.3 [reported] [P0] `reaction.added` executes side effects outside the per-phone lock
`functions/src/linq/webhooks.ts:2395`. `handleReactionAdded` runs
`executeBookings` / `handleTaskApproval` / `handleRecurringConfirm` with no
`claimInboundProcessing`, while `handleInbound` holds the lock at line 590. A
user tapping 👍 and texting "yes" within a second races the two against the same
`agent_tasks` `awaiting_approval` doc → double-executed booking / double charge.
**Fix:** run reactions through the same per-phone claim/lock as inbound messages.

### 1.4 [reported] [P0] Inbound dedup skipped when the webhook has no event id
`functions/src/linq/webhooks.ts:2534`. Guard is
`if (eventId && (await claimWebhookEvent(...)) === "duplicate")` — when `eventId`
is falsy, no claim is written and `handleInbound` runs unconditionally. A
redelivered `message.received` lacking an id re-drives the whole turn (duplicate
reply + duplicate side effects) since the per-phone lock is released once the
first turn finishes. **Fix:** synthesize a stable dedup key
(phone+timestamp+hash) when the provider omits an id, and fail closed.

### 1.5 [VERIFIED] [P1] Booking conflict check is a TOCTOU race
`functions/src/agents/bookingExecutor.ts:11`. `hasConflict()` reads appointments
and the write commits later (`batch.commit()`) with no transaction spanning the
check. Two overlapping bookings for the same caregiver arriving near-simultaneously
can both pass → double-booked. **Fix:** do the conflict re-check inside the
booking transaction.

### 1.6 [VERIFIED] [P1] Swap acceptance can double-book the accepting caregiver
`functions/src/agents/caregiverSwapHandler.ts:253`. The acceptance transaction
re-reads only the swap doc's `status`, never the accepting caregiver's own
calendar; conflict was checked once at broadcast (line 166). In the up-to-24h
window before acceptance the caregiver can be booked elsewhere and still win the
swap. **Fix:** re-check the accepter's own appointments inside the claim
transaction.

### 1.7 [VERIFIED] [P1] Availability check ignores minutes and the shift's end time
`functions/src/agents/caregiverSwapHandler.ts:158` and identical
`functions/src/agents/clientSwapRequestHandler.ts:128`. Only the shift's *start
hour* is tested against the slot (`shiftHour >= startH && shiftHour < endH`),
ignoring minutes and the shift end. A 13:00–18:00 shift matches a caregiver
available only 09:00–14:00. **Fix:** compare full start/end minute ranges.

### 1.8 [VERIFIED] [P1] Caregiver cancel writes with no status precondition
`functions/src/agents/caregiverCancelShiftHandler.ts:261`. Blind
`update({status:"cancelled"})` with no precondition/transaction; driven from
session state cached up to 30 min. If the shift was reassigned/completed by
another flow meanwhile, this clobbers it and fires a family alert + replacement
search for a shift that's no longer theirs. **Fix:** guard on current status in a
transaction.

### 1.9 [VERIFIED] [P1] Timesheet SMS APPROVE lacks the precondition the callable has
`functions/src/agents/timesheetHandler.ts:135`. The SMS path writes
`status:"approved"` with no precondition, unlike `reviewShiftHours`
(`shiftHours.ts:262`, throws `failed-precondition`). **Note:** the feared
double-charge is *mitigated* — the handler clears `timesheetStep` after the first
reply (line 186), and the payment trigger only fires on a transition *into*
payable status (`shiftHours.ts:785`) with idempotency-keyed transfers
(`:791/:845`). Add the precondition as defense-in-depth; not an active double-pay.

### 1.10 [VERIFIED] [P1] Schedule change leaves today's old visit untouched
`functions/src/agents/modifyScheduleFlow.ts:373`. `where("date", ">", today)`
(strictly greater) neither cancels nor regenerates today's old-schedule visit →
stale/duplicate visit for today when the change lands on today's weekday.
**Fix:** use `>=` and reconcile today explicitly.

### 1.11 [VERIFIED] [P2] Orphaned shift offer on a second concurrent offer
`functions/src/agents/shiftOffer.ts:89`. `pendingShiftOfferId` is overwritten
with no check for an already-open offer; the prior offer is orphaned until its 2h
TTL sweep (which then fires a replacement search). **Fix:** refuse/queue a new
offer while one is pending, or resolve the old one first.

### 1.12 [design] Client schedule-change commits the caregiver with no accept gate
`functions/src/agents/modifyScheduleFlow.ts:380`. Unlike booking/swap/time-change
(which gate through `shiftOffer`), a client schedule modification writes new
`confirmed` appointments and only sends the caregiver an FYI. Real consent
inconsistency — decide whether this is intended before "fixing".

## 2. Backend — scheduled cron jobs (P0/P1)

### 2.1 [VERIFIED] [P0] `!= true` reminder queries silently skip appointments missing the flag
`functions/src/scheduled/clientThirtyMinReminder.ts:24` (and
`thirtyMinShiftReminder.ts:22`, `dayBeforeShiftReminder.ts:27`,
`clientDayBeforeReminder.ts:33`, `preShiftFamilyCheckin.ts:44`,
`upcomingVisitReminder.ts:19`). Firestore `where("...Sent","!=",true)` excludes
documents where the field is **absent**; appointments created without the boolean
(e.g. `recurringScheduler.ts` writes none) are never returned and **never get a
reminder**. **Fix:** initialize the flag to `false` on appointment creation, or
query `where(...,"in",[false])` / `where(... ,"==", false)` with a backfill.

### 2.2 [reported] [P0] Timezone: wall-clock shift times parsed/compared as UTC
`functions/src/scheduled/thirtyMinShiftReminder.ts:96`,
`clientThirtyMinReminder.ts:100` (`new Date(\`${dateStr}T${hh}:${mm}:00\`)` has no
offset → parsed as UTC); `preShiftFamilyCheckin.ts:36`, `shiftTaskNudges.ts:116`
(`now.getHours()` is UTC, compared to local shift times). Cron has no
`.timeZone()`. Reminders/nudges fire hours off or never. **Fix:** anchor all
shift-time math to the business timezone (America/Los_Angeles).

### 2.3 [reported] [P0] Expired background checks stay bookable
`functions/src/scheduled/backgroundCheckExpiry.ts:66`. Sets
`backgroundCheckData.backgroundCheckStatus="expired"` but the query and
bookability gate read `backgroundCheckData.status` (still `"clear"`); expiry
never takes effect and the doc is re-processed daily forever. **Fix:** write the
field the gate actually reads.

### 2.4 [reported] [P0] Cron-vs-manual-trigger double-sends / double-books (no claim/lock)
`dndQueueProcessor.ts:12` (reads `sentAt==null`, stamps only after send →
overlapping run double-sends every queued SMS); `proactiveDraftSender.ts:50`
(approved drafts flipped to `sent` only after send → cron racing the admin
trigger double-sends); `weeklyDigest.ts:205` (writes
`weekly_digests/{userId}_{today}` but never reads it first → duplicate digests);
`healthTrends.ts:132` (no existing-doc check → re-sends monthly summary);
`recurringScheduler.ts:129` and `shiftGenerator.ts:79/:210` (no per-date
uniqueness / non-atomic first-run flag → duplicate shifts). **Fix:** claim rows
transactionally before sending; check the idempotency doc before re-sending.

### 2.5 [reported] [P1] Silent caps — `limit(N)` with no ordering deterministically starves the tail
`jobMatchNotifications.ts:33` (`limit(100)`),
`nextDayFamilyFeedback.ts:44`, `pendingTimesheetNudge.ts:64`,
`familySatisfactionCheckin.ts:37`, `familySilenceCheckin.ts:41` (`limit(500)`),
`inferActiveHours.ts:69` (`limit(300)`). Users past the cap are never processed —
e.g. **caregivers whose timesheets are never nudged stay unpaid indefinitely**.
**Fix:** paginate (cursor over ordered query), or process by
oldest-unprocessed with a stable order.

### 2.6 [reported] [P1] Un-chunked write batches throw past 500 ops
`nightlyMemory.ts:110` (one `batch.set` per client×weekday) and
`transportBadge.ts:32` (all badge updates in one batch) exceed the 500-op limit
at scale; the commit throws and **all** writes in that run are dropped (caught +
logged). **Fix:** chunk into ≤500-op batches.

## 3. Backend — memory, migrations, safety (P1/P2)

### 3.1 [VERIFIED] [P1] Senior→household migration is not idempotent
`functions/src/migrations/migrateSeniorsToHousehold.ts:30`. The skip check tests
`data.clientId`, but the migration only writes `migratedTo` to the old doc (line
59). A re-run re-migrates every senior → duplicate `senior_profiles` docs and
duplicate IDs appended to `users.seniorIds`, contradicting the "Safe to re-run"
comment. **Fix:** skip on `data.migratedTo`.

### 3.2 [VERIFIED] [P2] Rekey migration orphans the `payouts` subcollection
`functions/src/migrations/rekeyLegacyCaregiverDocs.ts:201`. `doc.ref.delete()`
doesn't cascade to subcollections, so `caregivers/{legacyId}/payouts/*` persists
after the parent is deleted (payouts were copied to the new doc first, so it's
dormant, not lost). **Fix:** delete subcollection docs before the parent.

### 3.3 [VERIFIED] [P2] `learnedFacts` dedup may return a superseded fact
`functions/src/memory/learnedFacts.ts:97`. `.where("_norm","==",norm).limit(1)`
with no ordering can return a superseded doc when an active one exists →
duplicate active fact instead of a weight bump. **Fix:** filter
`supersededAt == null` in the query, or fetch >1 and pick the active one.

### 3.4 [VERIFIED] [P2] `getRelevantFacts` filters superseded *after* the top-30 cut
`functions/src/memory/learnedFacts.ts:151`. `.orderBy("weight","desc").limit(30)`
then filters superseded (line 160); since weight isn't reset on supersession,
high-weight stale facts can crowd out active ones for users with >30 facts.
**Fix:** filter superseded in the query, or reset weight on supersession.

### 3.5 [VERIFIED] [P2] Memory consolidation can pick the wrong session
`functions/src/memory/memoryFiles.ts:425`.
`.where("userId","==",userId).limit(1)` with no ordering; a user with two
sessions (two phones, same uid) can get the wrong 7-day history consolidated.
**Fix:** order by most-recent activity, or require phone.

### 3.6 [VERIFIED] [P2] Crisis keyword "ER now" can never match
`functions/src/safety/crisisDetector.ts:17`. Input is lowercased (line 44) but
the keyword keeps a capital `ER`, so `lower.includes("ER now")` is always false.
Mitigated by `"emergency room"`/`"911"`/`"ambulance"` (lowercase) and the LLM
fallback. **Fix:** lowercase the keyword.

### 3.7 [VERIFIED] [P2] Linter strips banned words as substrings (no word boundaries)
`functions/src/safety/linter.ts:83`. `new RegExp(safePhrase,"gi")` has no `\b`
despite the "word-boundary-aware" comment; the list includes
`"leverage"`/`"utilize"`/`"synergy"`, so `"leveraging"` → `"ing"`, `"utilized"` →
`"d"` in outbound care messages. Cosmetic but real. **Fix:** wrap in `\b…\b`.

## 4. Frontend — money & data integrity (P0/P1)

### 4.1 [VERIFIED] [P0] Promo code shows a discount that isn't charged
`components/caregiver/CaregiverMembership.tsx:86`. The total displays

### 4.2 [VERIFIED] [P1] Double-submit inflates public caregiver ratings

`increment(1)`/`increment(rating)` on the caregiver's `totalReviews`/`ratingSum`.

### 4.3 [VERIFIED] [P1] Client-side conflict check uses the UTC date → double-book

### 4.4 [VERIFIED] [P1] Live appointment listener drops `doc.id`

### 4.5 [VERIFIED] [P1] `normalizePhoneNumber` passes malformed numbers as valid E.164

### 4.6 [reported] [P0] Auth-not-ready-on-refresh leaves the client unable to approve timesheets

### 4.7 [reported] [P0] Emergency button swallows failures silently
`components/client/FamilyEmergency.tsx:14`. A failed `v1-triggerFamilyEmergency`

## 6. Backend — MCP tool dispatch (P0/P1)

**Tool count:** `MCP_TOOLS` = **156** total (client surface `CLIENT_TOOLS` = 123,
caregiver surface `CAREGIVER_TOOLS` = 63). Neither role surface exceeds OpenAI's
128 cap **today**, but the client surface is only **5 tools** under it, and
`capToolsForOpenAi` (`agents/openaiToolLoop.ts:11,21`) **silently drops the tail**
(logs a warning, then `slice(0,128)`) if it ever crosses. **Action:** add a
build-time assertion that each role surface stays under 128, so a new client tool
can't silently disable another.

### 6.1 [VERIFIED] [P0] The care-plan subsystem is split across THREE divergent paths — versioning/restore is dead
`functions/src/mcp/server.ts`. Three different storage locations for one concept:
- `update_care_plan` (`:4244`) and `get_care_plan` (`:4231`) → **top-level**
  `care_plans/{clientId}` (keyed by **clientId**).
- `onCarePlanWrite` version trigger → `senior_profiles/{seniorId}/care_plans/{planId}`,
  writes snapshots to `.../carePlanVersions` (keyed by **seniorId**).
- `restore_care_plan_version` (`:6353`) → reads/writes
  `senior_profiles/{seniorId}/care_plans/active` and `.../carePlanVersions`.

Consequences: (a) agent care-plan edits never fire the version trigger → **no
history is ever recorded**; (b) `get_care_plan_history` (`:6314`) reads the
always-empty `carePlanVersions` subcollection → always returns nothing; (c)
`restore_care_plan_version` writes to `senior_profiles/{seniorId}/care_plans/active`
— a document **nobody reads** (the live plan is top-level `care_plans/{clientId}`)
→ a family "roll back my care plan" reports success but **changes nothing users
see**. In the household model `clientId ≠ seniorId`, so these subsystems can never
see each other's data. **Fix:** pick ONE canonical path+key for care plans and
route write, read, trigger, history, and restore through it.

### 6.2 [VERIFIED] [P1] `restore_care_plan_version` never verifies senior ownership
`functions/src/mcp/server.ts:6335`. Takes `clientId` from the (session-enriched)
input but only checks the senior/version docs **exist** — never that the senior
belongs to that client (contrast `update_senior_profile:4586`,
`add_family_member:4327`). A model-supplied `seniorId` from another household can
be restored/overwritten. Confirmation-gated, but the gate doesn't check ownership.
**Fix:** assert the senior is in the caller's household before restoring.

### 6.3 [VERIFIED] [P1] `update_preferences` writes LLM/session fields with no allowlist
`functions/src/mcp/server.ts:3454`. `const { userId, ...patch } = input; …set(patch,
{merge:true})`. Since qaAgent enriches every tool input with `phone`/`chatId`/
`clientId`/`userId`, and the schema only declares DND fields, a single call
persists `phone`/`chatId`/`clientId` plus any hallucinated key into
`user_preferences/{userId}`. **Fix:** allowlist the preference fields before write.

### 6.4 [reported] [P1] `trigger_emergency_alert` has no dedup — double-pages ops
`functions/src/mcp/server.ts:3335`. A CORE always-bound, non-confirmation-gated
tool that `add()`s a fresh `emergency_alerts` + `admin_alerts` doc each call; a
model retry/double-call spawns duplicate active alerts and pages ops twice.
**Fix:** dedup by (seniorId, type, short time window) or use the idempotency
ledger.

### 6.5 [reported] [P1] Idempotency is ad-hoc for money/state tools
`functions/src/mcp/server.ts:38` — only `perform_web_action` is in
`IDEMPOTENT_CONFIRMED_TOOLS` (ledger-guarded exactly-once). `retry_shift_payment`
(`:4104`), `update_booking_payment_method` (`:4142`), `confirm_cash_received`,
`select_callout_backup` (`:3383`) rely on ad-hoc `status ===` read-then-write
checks, not the ledger. Notably `retry_shift_payment` does a non-atomic
get-then-update on `status==="payment_failed"`; two confirmed retries racing the
async `onShiftHoursApproved` re-charge trigger can both flip to `approved` →
**double-charge window**. **Fix:** route confirmed money/state tools through the
idempotency ledger.

### 6.6 [reported] [P1] Tools that book/mutate on unvalidated model-supplied ids
- `select_callout_backup` (`:3383`) — assigns `backupCaregiverId` and flips status
  to `confirmed` **without** checking the id is in `appt.backupCaregiverOptions`;
  any existing caregiver id the model supplies gets booked onto the visit.
- `send_caregiver_message` (`:3612`) — no ownership check tying `clientId` to the
  caregiver's care team; any client session can SMS any caregiver by id (and a

- `save_onboarding_field` (`:6204`) — writes `fieldValue` verbatim with only a

### 6.7 [reported] [P2] `update_booking_payment_method` UTC date guard
`functions/src/mcp/server.ts:4142`. `new Date(appt.isoDate || appt.date)` — a bare
`"YYYY-MM-DD"` parses as UTC midnight, so a booking earlier the same day (US
timezone) can read as "not yet started" and have its payment method flipped to

### 6.8 [reported] [P2] `submit_shift_hours` NaN-duration path
`functions/src/mcp/server.ts:4937`. `hourlyRate` falls back to `22`,
